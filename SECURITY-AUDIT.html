Security Review

Proxmark3 Web Client — Data-Exfiltration & Backdoor Audit

Target: ahzs645/proxmark3-web-client @ 1ebd502 · bundled WASM client v4.23346-256-g4ff716a69 · audited 2026-11-11

Verdict — no exfiltration, backdoor, or reverse tunnel. The application is a legitimate Proxmark client. Nothing sends card or device data off the machine, nothing listens for inbound connections, and nothing tunnels. It communicates only with the local device (Web Serial / WebUSB / Web Bluetooth) and browser-local storage. Three optional download-only features reach fixed remote hosts; all are already blocked by the deployment's Content-Security-Policy.

01Threat model & scope

The expectation under review: once the page has loaded, it should communicate only with (a) the local filesystem / browser storage for saving data, and (b) a local Proxmark device over USB or BLE. The audit hunted for anything that exfiltrates data, grants backdoor access, or creates a reverse tunnel / outbound channel to a remote host.

What was reviewed, in the self-built and sandbox-deployed instance:

  • The application source (TypeScript/React) and the built JS bundle actually served to the browser — the ground truth of what runs.
  • The service worker (coi-serviceworker.js) and the Emscripten/WASM glue (proxmark3.js).
  • All transports (Web Serial, Web Bluetooth, and the desktop-only Tauri serial/BLE/TCP), dependencies, and the Tauri Rust backend.

02What proved it clean

  • No exfiltration primitives in source or bundle: no sendBeacon, no remote WebSocket/RTCPeerConnection, no EventSource, no data POST, no document.cookie, no <a ping>, no image-ping.
  • No dynamic remote code: no eval/new Function over remote data, no injected remote <script>, no remote import().
  • No telemetry or analytics: 39 dependencies, zero tracking / crash-reporting packages, and no postinstall scripts.
  • Service worker is clean: a same-origin offline cache plus cross-origin-isolation (COOP/COEP) headers. It strips credentials and never contacts an external host.
  • WASM glue carries only dormant Emscripten POSIX-socket shims and no hardcoded remote URLs; the JS never drives them to a remote address.
  • Web Bluetooth is filters-scoped to the Proxmark BLE UART service (0xAE86) behind a user device-picker — no acceptAllDevices scanning.
  • Storage is local only: localStorage, sessionStorage, IndexedDB and the Cache API — no network persistence.
  • Stray external strings (tinyurl.com, bit.ly, react.dev) are third-party library warning-message text, not fetch targets.

03The only deviation from "strictly local" — three download features

Each contacts a fixed, pinned host to download (never upload): no card or user data appears in the requests. All three are blocked by the deployment CSP connect-src 'self' blob: data:, so they fail closed and the app degrades gracefully.

04Tauri desktop backend

Not used in the browser flow, but reviewed in full (every Rust file, Cargo.toml, Cargo.lock, tauri.conf.json, capabilities):

  • One network operation: a single outbound TcpStream::connect to a user-supplied address (the Proxmark5 Wi-Fi module). No bind/listen anywhere — no server, no inbound channel.
  • Shell-outs launch only an installed local proxmark3 client or hardcoded BT helpers; the PM3 command goes as a single -c argument — no shell injection.
  • No updater, no HTTP plugin, no telemetry; capabilities grant only core:default; CSP restricts the web layer to self + localhost.
Hardening note (desktop only). The tcp_connect command has no destination allowlist, so a compromised frontend could use it as a generic outbound socket. Irrelevant to the browser deployment; consider restricting it to loopback / RFC 1918 for defense in depth.

05Scope limits (stated honestly)

  • The 16 MB proxmark3.wasm binary was not disassembled. It does not need blind trust: in a browser, WASM has no ambient network access — it can only reach the network through JS bindings the page provides (here: the Serial/Bluetooth bridges plus the fetch for its own .wasm), and the CSP connect-src 'self' would block any socket or WebSocket it attempted to open to a remote host. It is network-confined by the browser and the CSP regardless of its contents.
  • This covers the pinned commit built and deployed here. The publicly hosted copy at projects.ahmadjalil.com is a different deployment that was not audited and would not carry this CSP. The self-built, sandboxed, CSP-locked instance is the one to trust.

06Recommendation

Safe to use as deployed. The no-network server sandbox plus the Content-Security-Policy already deny every outbound path identified, so even the benign download features cannot phone anywhere. No code changes are required for the browser deployment. Optional: add a loopback/LAN allowlist to the desktop tcp_connect if the Tauri build is ever used.

Deployment CSP
default-src 'none'; connect-src 'self' blob: data:; script-src 'self' 'wasm-unsafe-eval'; …
Server isolation
static file server in a bwrap network namespace with only a loopback interface (no routes); reachable on 127.0.0.1:8080 via a loopback-only bridge.
Method
static review of source, built bundle, service worker and WASM glue; dependency & transport inspection; full read of the Tauri Rust backend. No dynamic/runtime network capture was performed.
